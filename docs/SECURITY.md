## Strict Security & AppSec Mandates

### Server Actions Security (Critical)

- **Always Validate Inputs:** Every single Server Action (`"use server"`) must parse and validate incoming data using a strict schema library (e.g., Zod) as its first line of defense.
- **Backend Authentication Verification:** Never pass the User ID or Session state from the client UI as a parameter to a Server Action. Always initialize the Supabase client inside the action via `@supabase/ssr` cookies and fetch the user using `await supabase.auth.getUser()`. Never substitute `getSession()` for this check — `getSession()` reads a locally-stored JWT without revalidating it against the Supabase Auth server, so it can trust a stale or tampered session. `getUser()` is mandatory anywhere authorization decisions are made.
- **Authorization Beyond RLS:** RLS protects direct database reads/writes, but it is not a substitute for explicit authorization checks inside a Server Action. Any action that performs a non-DB side effect (calling a third-party API, sending an email, triggering a webhook, writing to external storage) must independently verify the authenticated user is allowed to perform that specific operation before executing it.
- **Fail Securely:** Catch database exceptions internally (`console.error`). Return a structured, generic object to the client UI (e.g., `{ success: false, error: "An unexpected error occurred." }`). Never reveal raw system, Postgres, or internal schema errors to the client. This applies equally to Zod validation failures — return the same generic error shape, not raw field-level constraint or schema details.
- **Rate Limiting Review:** Server Actions are reachable as unauthenticated-adjacent POST endpoints under the hood. Any action that mutates state, sends external requests, or triggers a side effect must be flagged for rate-limiting review before shipping.

### Supabase Database & Isolation

- **Day-One Row Level Security (RLS):** Every table creation or alteration schema must include explicit SQL commands enabling RLS (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
- **Policy Enforcement:** Define explicit Postgres policies (`FOR SELECT`, `FOR INSERT`, `FOR UPDATE`) bound to authenticated users via `auth.uid()`. Assume public access is denied by default.
- **Policy Verification (Required):** A policy is not considered complete on creation alone. Every new or modified RLS policy must be tested by attempting the same operation as a non-owner authenticated user before merge, to catch logic errors (e.g., conditions that unintentionally match on `NULL`, or overly permissive `USING`/`WITH CHECK` clauses).
- **No Hardcoded Tokens:** All interactions must pass through the typed Supabase Client context. Never expose or hardcode the Service Role key anywhere in the client code bundle.

### Service-role exception: cron routes

- The service-role client (`src/lib/supabase/admin-client.ts`) bypasses RLS and is otherwise only used after an explicit admin-role check. The exception is **cron routes under `/api/cron/`**, which run with no user. There are two:
  - `/api/cron/fx-rates` — upserts `fx_rates` only.
  - `/api/cron/hts-release` — imports the USITC HTS for the Tariff Calculator. Touches only `hts_releases`, `hts_lines`, and the `activate_hts_release()` function (executable by `service_role` only; refuses to activate a partial import). Its database access is confined to `src/lib/tariff/hts-import-store.ts`.
- A third, narrow exception is **saving a duty estimate** (next section). It is not a cron route and never runs without a signed-in user.
- Each cron route must call `isAuthorizedCronRequest()` (`src/lib/cron-auth.ts`) before anything else: it requires `Authorization: Bearer <CRON_SECRET>`, compares in constant time, and fails closed when `CRON_SECRET` isn't set. Vercel Cron sends this header automatically.
- The proxy's login redirect (`src/proxy.ts`, Next.js 16's replacement for `middleware.ts`) skips exactly the `/api/cron/` prefix (`CRON_ROUTE_PREFIX` in `src/lib/supabase/middleware.ts`) and nothing else; security headers still apply.
- Keep each cron route's service-role use to the tables it maintains (listed above). Treat the external data it fetches as untrusted: validate it (Zod) before writing. The HTS import validates every exported row, strips markup from descriptions, and rejects a chapter whole if any row is malformed.

### Tariff editor permission

- `app_metadata.tariff_editor = true` (set only by admins through `updateTariffEditor` in /admin, via the service role after an admin check; users can't edit app_metadata) lets a user maintain duty and fee data. SQL `is_tariff_editor()` (editor or admin) gates writes to `customs_fees`, `additional_duties`, `additional_duty_scope` and `duty_program_reviews`, and nothing else. The duty-data server actions check the same permission (`getTariffPermissions`, using `getUser`) before writing.
- Rates in `additional_duties` can't be edited in place (trigger; a row can't become conditional or unconditional in place either); every change to duties, scope and fees is written to `tariff_data_history` by a security-definer trigger that nobody can write to directly. Whether a row's condition is assumed (`assume_condition`) is editable by tariff editors like other details and, like any change, puts the program back to pending review. The one exception is an update that changes only a row's source fields (`source_label`, `source_url`, `source_checked_on`, `source_document_url`, `source_document_label`): it is still recorded in the history, but `duty_program_review_status` ignores it (`tariff_history_is_source_only()`), since rates and scope are unchanged. `additional_duty_scope_counts` is a `security_invoker` view (signed-in read, anon revoked).

### Service-role exception: saveEstimate (`save_duty_estimate`)
- Why: amounts are calculated on the server (rate parser, exact arithmetic, additional-duty rules, all TypeScript). If signed-in users could insert into `duty_estimates` themselves, they could store any internally consistent numbers through the API. The database can't tell our server from a user holding the same session, and can't recompute a duty, so the server proves itself with the service-role key and the database re-checks what it can.
- Use: `saveEstimate` (`tariff-calculator/actions.ts`) calls `saveDutyEstimate()` in `src/lib/tariff/estimate-store.ts` **only after** `getUser()`, the project/quote ownership check, the unchanged-sources check, every confirmation and the server-side calculation. That file is the only place the service-role client is used for estimates, and it calls `rpc("save_duty_estimate")` and nothing else (`service-role-use.test.ts` fails on any other use of the service-role client, or any other call in the store). Previews, reads and deletes stay on the user's client. There is no `server-only` package in this project, so the guard is that test plus this rule.
- The function (`security definer`, `search_path=''`): `EXECUTE` is revoked from PUBLIC, `anon` and `authenticated` and granted to `service_role` only. (Supabase's default privileges give `service_role` full table privileges, and the key bypasses RLS, so the service key could still insert into `duty_estimates` directly. What confines it to the function is the code, `service-role-use.test.ts`, not a database privilege. Revoking `INSERT` from `service_role` would make the function the only way even for the key, since the function is `security definer`; not done.) It reads only an allow-list of fields (anything else, such as `id`, `created_by` or `created_at`, is refused), sets `created_by` from the user id it is given, and checks: the user exists; a linked row's project is owned by that user or the user is an admin (`is_admin_user()`, the same fact as `is_admin()`, read from `auth.users.raw_app_meta_data` instead of the JWT); the quote belongs to the project (trigger); the HTS line, its description, ancestors, special rate and base rate text match the **current** release; the rate column matches the country (column 2); the as-of date (the day it was calculated) is today or yesterday in UTC (the app's `todayUtc()`); the expected `entry_date` (optional, defaults to the as-of date) is from a day before to 366 days after it, and the column 2 rule is judged on it; a daily-feed exchange rate is the stored `fx_rates` rate; the customs value equals value × rate less any deduction; the duty, additional and fee line amounts add up to the totals; and the table's own constraints.
- The key's intermittent PGRST303 error (clock skew) is retried briefly (3 attempts, about 3 s; `retryOnPgrst303` with short delays). PGRST303 is answered before the function runs, so a retry can't save twice. Any other error is logged and the user sees "Couldn't save the estimate right now. Try again."
- **What this does not prevent:** a user can still choose any inputs (a low customs value, a different code) and the estimate will correctly calculate what they asked, with the inputs recorded in the snapshot; the base and additional duty amounts themselves aren't checked in the database (they're right because the server computed them); a leaked service-role key, or a bug in `saveEstimate`, is still serious, because the key can do far more than call this function.
- **Rollout:** step 1 added the function and the code; step 2 (migration `20261006151253_revoke_duty_estimates_insert`) revoked `INSERT` from `public`, `anon` and `authenticated` and dropped the insert policy, so signed-in users can no longer insert estimates themselves (a direct insert fails with `42501 permission denied for table duty_estimates`; pgTAP 16). **Rolling back** if saving ever breaks: add a new migration that re-grants (`grant insert on duty_estimates to authenticated;`) and recreates the policy (`create policy "Users can save their own duty estimates" on duty_estimates for insert to authenticated with check (created_by = auth.uid() and (forwarder_project_id is null or exists (select 1 from forwarder_projects fp where fp.id = duty_estimates.forwarder_project_id and (fp.owner_id = auth.uid() or is_admin()))));`), then `npx supabase db push`. Never edit an applied migration.

### Duty estimates linked to forwarder projects
- `duty_estimates` rows are locked (no update privilege plus a trigger), and **direct inserts are revoked**: signed-in users and anon can't insert, and the only way in is `save_duty_estimate` (service role, above), which applies the owner/admin rule for a linked row (a project's owner or an admin) and the quote-belongs-to-project trigger. The save and preview actions also check the owner/admin rule (`getOwnershipContext`), re-read the project and quote, refuse if they changed since the page loaded, require every input to be confirmed, and build the input snapshot from the database, never the form. Linked rows cascade-delete with their project or quote (a delete, which the lock allows).
- Linked estimates reach the Expert CSV only; client exports never carry them (`export-leak.test.ts`).

### HTS code lookup
- The lookup is a popup in the calculator form (the old `/tariff-calculator/hts-lookup` page redirects to `/tariff-calculator`). It runs through two server actions, `searchHtsAction` and `browseHtsHeadingAction` (`hts-lookup-actions.ts`): each checks `auth.getUser()` first, validates input (the query with Zod in `parseLookupQuery`: 100 characters, up to 8 words of lowercase letters and digits, or 2–10 digits; the heading as exactly 4 digits), fixes the row limit on the server (150 search, 500 browse), uses the signed-in user's Supabase client (never the service role), logs the real error server-side and returns a generic message.
- `search_hts_lines()` is `security invoker` (RLS applies: signed-in users read `hts_lines`), read-only, and executable by `authenticated` only (revoked from `public` and `anon`). It searches the current release only and refuses anything but lowercase letters and digits (22023), so nothing typed can carry tsquery syntax. It's called through supabase-js `rpc()` with parameters; no SQL is built from user input. `activate_hts_release()` (service role only) also fills `hts_lines.ancestor_text`.
- "Use this code" only sets the calculator form's HTS field (client state); the popup renders outside the `<form>`, so it can't submit it. Nothing writes to `forwarder_projects` (tests in `actions.test.ts` and pgTAP 14); the saved estimate's code is re-checked by the estimate actions as before.

### Secrets Management

- All keys (`NEXT_PUBLIC_SUPABASE_URL`, etc.) must be read exclusively from environment variables.
- If a new environment dependency is introduced, document it instantly inside `.env.example` with fallback placeholder variables.
