## Strict Security & AppSec Mandates

### Server Actions Security (Critical)

- **Always Validate Inputs:** Every single Server Action (`"use server"`) must parse and validate incoming data using a strict schema library (e.g., Zod) as its first line of defense.
- **Backend Authentication Verification:** Never pass the User ID or Session state from the client UI as a parameter to a Server Action. Always initialize the Supabase client inside the action via `@supabase/ssr` cookies and fetch the user using `await supabase.auth.getUser()`. Never substitute `getSession()` for this check — `getSession()` reads a locally-stored JWT without revalidating it against the Supabase Auth server, so it can trust a stale or tampered session. `getUser()` is mandatory anywhere authorization decisions are made.
- **Authorization Beyond RLS:** RLS protects direct database reads/writes, but it is not a substitute for explicit authorization checks inside a Server Action. Any action that performs a non-DB side effect (calling a third-party API, sending an email, triggering a webhook, writing to external storage) must independently verify the authenticated user is allowed to perform that specific operation before executing it.
- **Fail Securely:** Catch database exceptions internally (`console.error`). Return a structured, generic object to the client UI (e.g., `{ success: false, error: "An unexpected error occurred." }`). Never reveal raw system, Postgres, or internal schema errors to the client. This applies equally to Zod validation failures — return the same generic error shape, not raw field-level constraint or schema details.
- **Rate Limiting Review:** Server Actions are reachable as unauthenticated-adjacent POST endpoints under the hood. Any action that mutates state, sends external requests, or triggers a side effect must be flagged for rate-limiting review before shipping.

### Supabase Database & Isolation

- **Day-One Row Level Security (RLS):** Every table creation or alteration schema must include explicit SQL commands enabling RLS (`ALTER TABLE ... ENABLE ROW LEVEL SECURITY;`).
- **Policy Enforcement:** Define explicit Postgres policies (`FOR SELECT`, `FOR INSERT`, `FOR UPDATE`) bound to authenticated users via `auth.uid()`. Assume public access is denied by default.
- **Policy Verification (Required):** A policy is not considered complete on creation alone. Every new or modified RLS policy must be tested by attempting the same operation as a non-owner authenticated user before merge, to catch logic errors (e.g., conditions that unintentionally match on `NULL`, or overly permissive `USING`/`WITH CHECK` clauses).
- **No Hardcoded Tokens:** All interactions must pass through the typed Supabase Client context. Never expose or hardcode the Service Role key anywhere in the client code bundle.

### Service-role exception: cron routes

- The service-role client (`src/lib/supabase/admin-client.ts`) bypasses RLS and is otherwise only used after an explicit admin-role check. The exception is **cron routes under `/api/cron/`**, which run with no user. There are two:
  - `/api/cron/fx-rates` — upserts `fx_rates` only.
  - `/api/cron/hts-release` — imports the USITC HTS for the Tariff Calculator. Touches only `hts_releases`, `hts_lines`, and the `activate_hts_release()` function (executable by `service_role` only; refuses to activate a partial import). Its database access is confined to `src/lib/tariff/hts-import-store.ts`.
- Two more narrow exceptions are **saving a duty estimate** and **creating client users** (their own sections below). Neither is a cron route, and neither runs without a signed-in staff user.
- Each cron route must call `isAuthorizedCronRequest()` (`src/lib/cron-auth.ts`) before anything else: it requires `Authorization: Bearer <CRON_SECRET>`, compares in constant time, and fails closed when `CRON_SECRET` isn't set. Vercel Cron sends this header automatically.
- The proxy's login redirect (`src/proxy.ts`, Next.js 16's replacement for `middleware.ts`) skips exactly the `/api/cron/` prefix (`CRON_ROUTE_PREFIX` in `src/lib/supabase/middleware.ts`) and nothing else; security headers still apply.
- Keep each cron route's service-role use to the tables it maintains (listed above). Treat the external data it fetches as untrusted: validate it (Zod) before writing. The HTS import validates every exported row, strips markup from descriptions, and rejects a chapter whole if any row is malformed.

### Tariff editor permission

- `app_metadata.tariff_editor = true` (set only by admins through `updateTariffEditor` in /admin, via the service role after an admin check; users can't edit app_metadata) lets a user maintain duty and fee data. SQL `is_tariff_editor()` (editor or admin) gates writes to `customs_fees`, `additional_duties`, `additional_duty_scope` and `duty_program_reviews`, and nothing else. The duty-data server actions check the same permission (`getTariffPermissions`, using `getUser`) before writing.
- Display names are admin-only: `app_metadata.first_name`, set by `updateUserDisplayName` and `createUser` in /admin (service role, after an admin check), mirrored into `profiles.first_name` by the `handle_new_or_updated_user()` trigger (`security definer`, `search_path=''`). Nothing reads `user_metadata`, which users can rewrite with `auth.updateUser`; `src/lib/auth/user-metadata-use.test.ts` enforces that (pgTAP 23).
- Access needs a **staff** role an admin assigned. `has_staff_role()` (renamed from `has_app_role()` in `20261012131014`; `security definer`, `search_path=''`, live `auth.users`, executable by `authenticated`) is true only for `app_metadata.role` in `admin`/`logistics_expert`, never `client` (kept equal to `STAFF_ROLES` by `src/lib/auth/role-list-sync.test.ts`, which also fails if `client` is added). Every internal RLS table has a RESTRICTIVE `for all` policy `(select public.has_staff_role())`, run once per query, so an account without a staff role (no role, or a client user) reads and writes nothing (pgTAP 24, 28). The service-role paths check it too: `save_duty_estimate` (`has_staff_role_user(uuid)`, service role only) and `saveEstimate`. Signed-in users and anon hold no TRUNCATE, which RLS doesn't cover (pgTAP 24). Signup is off (`[auth] enable_signup = false` locally, the dashboard in production); users are created by admins with a role.
- Role checks read the current role, never the session token. `is_admin()` and `is_tariff_editor()` are `security definer` (`search_path=''`, stable, executable by `authenticated` and `service_role`, not `anon`) and read `auth.users.raw_app_meta_data` for `auth.uid()`, the same source as `getUser()` and `is_admin_user()`. They never read `raw_user_meta_data`, which users can edit. A promotion, demotion or editor change applies on the user's next request, with no sign-in needed; a token for a deleted user is neither admin nor editor (pgTAP 22).
- Rates in `additional_duties` can't be edited in place (trigger; a row can't become conditional or unconditional in place either); every change to duties, scope and fees is written to `tariff_data_history` by a security-definer trigger that nobody can write to directly. Whether a row's condition is assumed (`assume_condition`) is editable by tariff editors like other details and, like any change, puts the program back to pending review. The one exception is an update that changes only a row's source fields (`source_label`, `source_url`, `source_checked_on`, `source_document_url`, `source_document_label`): it is still recorded in the history, but `duty_program_review_status` ignores it (`tariff_history_is_source_only()`), since rates and scope are unchanged. `additional_duty_scope_counts` is a `security_invoker` view (signed-in read, anon revoked).

### Service-role exception: saveEstimate (`save_duty_estimate`)
- Why: amounts are calculated on the server (rate parser, exact arithmetic, additional-duty rules, all TypeScript). If signed-in users could insert into `duty_estimates` themselves, they could store any internally consistent numbers through the API. The database can't tell our server from a user holding the same session, and can't recompute a duty, so the server proves itself with the service-role key and the database re-checks what it can.
- Use: `saveEstimate` (`tariff-calculator/actions.ts`) calls `saveDutyEstimate()` in `src/lib/tariff/estimate-store.ts` **only after** `getUser()`, the project/quote ownership check, the unchanged-sources check, every confirmation and the server-side calculation. That file is the only place the service-role client is used for estimates, and it calls `rpc("save_duty_estimate")` and nothing else (`service-role-use.test.ts` fails on any other use of the service-role client, or any other call in the store). Previews, reads and deletes stay on the user's client. There is no `server-only` package in this project, so the guard is that test plus this rule.
- The function (`security definer`, `search_path=''`): `EXECUTE` is revoked from PUBLIC, `anon` and `authenticated` and granted to `service_role` only. (Supabase's default privileges give `service_role` full table privileges, and the key bypasses RLS, so the service key could still insert into `duty_estimates` directly. What confines it to the function is the code, `service-role-use.test.ts`, not a database privilege. Revoking `INSERT` from `service_role` would make the function the only way even for the key, since the function is `security definer`; not done.) It reads only an allow-list of fields (anything else, such as `id`, `created_by` or `created_at`, is refused), sets `created_by` from the user id it is given, and checks: the user exists; a linked row's project is owned by that user or the user is an admin (`is_admin_user()`, the same fact as `is_admin()`, read from `auth.users.raw_app_meta_data` instead of the JWT); the quote belongs to the project (trigger); the HTS line, its description, ancestors, special rate and base rate text match the **current** release; the rate column matches the country (column 2); the as-of date (the day it was calculated) is today or yesterday in UTC (the app's `todayUtc()`); the expected `entry_date` (optional, defaults to the as-of date) is from a day before to 366 days after it, and the column 2 rule is judged on it; a daily-feed exchange rate is the stored `fx_rates` rate; the customs value equals value × rate less any deduction; the duty, additional and fee line amounts add up to the totals; and the table's own constraints.
- The key's intermittent PGRST303 error (clock skew) is retried briefly (3 attempts, about 3 s; `retryOnPgrst303` with short delays). PGRST303 is answered before the function runs, so a retry can't save twice. Any other error is logged and the user sees "Couldn't save the estimate right now. Try again."
- **What this does not prevent:** a user can still choose any inputs (a low customs value, a different code) and the estimate will correctly calculate what they asked, with the inputs recorded in the snapshot; the base and additional duty amounts themselves aren't checked in the database (they're right because the server computed them); a leaked service-role key, or a bug in `saveEstimate`, is still serious, because the key can do far more than call this function.
- **Rollout:** step 1 added the function and the code; step 2 (migration `20261006151253_revoke_duty_estimates_insert`) revoked `INSERT` from `public`, `anon` and `authenticated` and dropped the insert policy, so signed-in users can no longer insert estimates themselves (a direct insert fails with `42501 permission denied for table duty_estimates`; pgTAP 16). **Rolling back** if saving ever breaks: add a new migration that re-grants (`grant insert on duty_estimates to authenticated;`) and recreates the policy (`create policy "Users can save their own duty estimates" on duty_estimates for insert to authenticated with check (created_by = auth.uid() and (forwarder_project_id is null or exists (select 1 from forwarder_projects fp where fp.id = duty_estimates.forwarder_project_id and (fp.owner_id = auth.uid() or is_admin()))));`), then `npx supabase db push`. Never edit an applied migration.

### Duty estimates linked to forwarder projects
- `duty_estimates` rows are locked (no update privilege plus a trigger), and **direct inserts are revoked**: signed-in users and anon can't insert, and the only way in is `save_duty_estimate` (service role, above), which applies the owner/admin rule for a linked row (a project's owner or an admin) and the quote-belongs-to-project trigger. The save and preview actions also check the owner/admin rule (`getOwnershipContext`), re-read the project and quote, refuse if they changed since the page loaded, require every input to be confirmed, and build the input snapshot from the database, never the form. Linked rows cascade-delete with their project or quote (a delete, which the lock allows).
- Linked estimates reach the Expert CSV only; client exports never carry them (`export-leak.test.ts`).

### HTS code lookup
- The lookup is a popup in the calculator form (the old `/tariff-calculator/hts-lookup` page redirects to `/tariff-calculator`). It runs through two server actions, `searchHtsAction` and `browseHtsHeadingAction` (`hts-lookup-actions.ts`): each checks `auth.getUser()` first, validates input (the query with Zod in `parseLookupQuery`: 100 characters, up to 8 words of lowercase letters and digits, or 2–10 digits; the heading as exactly 4 digits), fixes the row limit on the server (150 search, 500 browse), uses the signed-in user's Supabase client (never the service role), logs the real error server-side and returns a generic message.
- `search_hts_lines()` is `security definer` (since `20261009124712`: with the role policy on `hts_lines`, Postgres won't use the full-text index under RLS because `@@` isn't leakproof). It applies the staff rule itself first (`has_staff_role()`; no staff role, no rows, so client users get nothing) and reads only `hts_lines`, `hts_releases` and the duty programs, which only staff can read. It is read-only, and executable by `authenticated` only (revoked from `public` and `anon`). It searches the current release only and refuses anything but lowercase letters and digits (22023), so nothing typed can carry tsquery syntax. It's called through supabase-js `rpc()` with parameters; no SQL is built from user input. `activate_hts_release()` (service role only) also fills `hts_lines.ancestor_text`.
- "Use this code" only sets the calculator form's HTS field (client state); the popup renders outside the `<form>`, so it can't submit it. Nothing writes to `forwarder_projects` (tests in `actions.test.ts` and pgTAP 14); the saved estimate's code is re-checked by the estimate actions as before.

### Landed Cost workspaces (Phase 2b)
- Five staff-only tables (`landed_cost_workspaces`, `_sku_lines`, `_scenarios`, `_scenario_items`, `_other_costs`; migrations `20261021013030` and `20261021013541`). They hold **inputs only**: no duty, fee or total is stored, and results are recalculated on the server.
- RLS on all five, each with the restrictive "Requires a staff role" policy. Any staff member reads. A workspace is inserted only as its own owner (`owner_id = auth.uid()`, even for admins) and updated or deleted by its owner or an admin; child rows are written only by the owner of their workspace or an admin (an `exists` check on the parent, which staff can read under RLS). Clients and anon get nothing; anon and `service_role` hold no privileges on these tables.
- Update privilege is granted per column, on the inputs only: `owner_id`, ids, `workspace_id`, `scenario_id`, `sku_line_id`, `currency` and `created_at` can't be changed by anyone through the API, so a workspace can't be given away and a row can't move between workspaces. Composite foreign keys (`(scenario_id, workspace_id)`, `(sku_line_id, workspace_id)`, and the baseline's `(baseline_scenario_id, id)`) make a row that mixes two workspaces impossible.
- No security definer function. The helpers (`landed_cost_text_ok`, `landed_cost_entered_value_ok`) and the trigger functions (row limits, entered value) run as the caller. Limits: 100 SKU lines and 5 scenarios per workspace, 20 other costs per scenario (triggers, under a per-workspace advisory lock), with check constraints matching the app's parsers. Tested by pgTAP 37; 03, 24 and 28 cover the tables too.
- `loadWorkspace` (`src/lib/landed-cost/server-workspace.ts`) reads through the caller's client, parses every row with Zod and returns generic messages; database errors are logged server-side only.

### Landed Cost draft saving (Phase 2c-1)
- Two functions (migration `20261021020238`), both **security invoker** with an empty `search_path`, executable by `authenticated` only (revoked from `public`, `anon` and `service_role`): `create_landed_cost_workspace(jsonb)` (a workspace and its first scenario, which becomes the baseline) and `save_landed_cost_draft(uuid, timestamptz, jsonb)` (the whole draft in one transaction). Running as the caller, they are bound by RLS, the column grants and every 2b check and trigger, exactly like direct writes; any failure rolls the whole call back. Neither is in pgTAP 32's tripwire, which lists security-definer functions only.
- Each function refuses any payload key it doesn't list (`owner_id`, `workspace_id`, `currency` can't be smuggled in); the owner comes from `auth.uid()`. A save locks the workspace row (`select … for update`, which needs the update policy, so only the owner or an admin gets past it: anyone else gets 42501), refuses a stale `updated_at` (LC409, compared as `timestamptz` to the microsecond), updates rows only `where workspace_id` matches (a row id from another workspace is refused), and refuses a draft with no scenario. To a client the workspace doesn't exist (P0002).
- The Server Actions (`src/app/(authenticated)/landed-cost/actions.ts`) start with `requireStaff()`, accept inputs only (every number a string; no computed amount is read from the browser), parse and normalise with Zod before any database call (`parse-draft.ts`), check owner-or-admin themselves to say so plainly, and map database errors to fixed messages (`draft-errors.ts`): no SQL or constraint text reaches the user. Results are calculated on the server on every load (`server-compute.ts`) and never stored. Tested by pgTAP 38 and Vitest.

### Client users (external)

Client users are **external** people (a client's own staff) who sign in to the client portal. They are the first users who aren't Move staff, so the rule is: they see nothing internal, ever.

- **Identity:** `app_metadata.role = 'client'` plus `app_metadata.client_id`, written only by the server (`create-client-user.ts`, below). Users can't edit `app_metadata`. `user_metadata` is never read (`user-metadata-use.test.ts`).
- **Database:** `has_staff_role()` excludes `client`, so every internal table's restrictive policy gives them 0 rows and no writes. pgTAP 28 checks this against the catalog for every table and view (so new ones are covered), plus every insert, update, delete, truncate and RPC (`create_*_with_client`, `search_hts_lines`, `save_duty_estimate`). `is_client_user()` and `my_client_id()` (`security definer`, `search_path=''`, live `auth.users`, anon revoked; `my_client_id()` is null unless the role is `client` and never raises on bad metadata) are for client-facing policies.
- **The one table a client may read:** `client_entitlements` (its client's plan). Its restrictive policy is "staff, or `client_id = my_client_id()`" for reads and staff-only for writes; only `is_admin()` may insert, update or delete; `granted_by` is forced to `auth.uid()` by a trigger. No row (or an expired `valid_until`) means free (`src/lib/client-tiers.ts`). pgTAP 29. Any future client-readable table must be named in pgTAP 24 and 28 on purpose.
- **Integrity:** `profiles.client_id` mirrors `app_metadata.client_id` (trigger), with a foreign key to `clients` (RESTRICT) and a check that only clients, and every client, have one. So a client user can't exist without a real client, a staff account can't carry one, and a client with portal users can't be deleted (pgTAP 30). Because the mirror runs on every `auth.users` update, a client user whose metadata is made inconsistent (for example in the dashboard) can't sign in until it's fixed: it fails closed.
- **App layers:** the proxy (`src/lib/auth/portal-routing.ts`, applied in `src/lib/supabase/middleware.ts` from live `getUser()` metadata) sends client users to `/portal` and 404s every other path, Server Action POSTs included; staff get a 404 for `/portal`. Server Actions are reachable from any route by a direct POST, so the proxy is only the first layer: every staff Server Action starts with `await requireStaff()` (404 unless staff; the /admin actions start with the admin check), and every portal page and action with `await requireClient()`. `server-action-guard.test.ts` parses every `"use server"` file and fails if an exported action doesn't start with its guard. The staff layout also 404s client users.
- **First sign-in:** client users start with `must_change_password`. Until it's cleared the proxy lets them reach only `/portal/change-password`. One Server Action (`changePassword`) changes the password as the user (`auth.updateUser`) and only then calls `complete_password_change()`, which removes the flag for the caller only, and only for a client. Calling that function directly without changing the password is possible but only affects the caller's own account.
- **Client writes are refused while `must_change_password` is set** (Phase 3a). Whoever created the account (or reset its password) has seen the one-time password, so until the client has chosen their own, an approval or request "from the client" could be the staff member's. `submit_client_request()` reads the flag live from `auth.users` and refuses (pgTAP 34); the Server Action and the proxy refuse too. Any future client write must do the same.
- **No email:** there's no custom SMTP, so there are no invite or password-reset emails (docs/TECH_DEBT.md). Staff pass the one-time password on themselves, ideally by a different channel from the email address.

### Client updates (what a client will be able to read)

A client update is a snapshot of one engagement that an expert deliberately publishes (`client_updates`, Phase 2a). It is the only project information that will ever reach a client.

- **What clients can read (Phase 2b):** their own client's **published** updates, through functions only. `client_updates` and `client_update_inputs` keep the standard restrictive staff policy, so a client reading either table directly gets 0 rows (pgTAP 28, 31, 32): row-level security can't hide columns, and the table also holds staff ids (`published_by`, `created_by`) and project ids.
  - `my_portal_updates()` (client users): no arguments; the client is always `my_client_id()`, read live from `app_metadata` (a `client_id` in `user_metadata` or claimed in a token is ignored). Returns published rows only, with client-safe columns only (stage, headline, summary, next step and due date, needs-action, published date, payload, project kind) and an `engagement_key` hashed from the client and the project, so it can't be compared across clients or turned back into an id.
  - `portal_updates_for_client(id)` (staff, for "View as client"): the same rows for any client, nothing for anyone else. Both wrap `portal_updates_rows(id)`, which no signed-in user can call directly.
  - `my_move_contact_names()`: the first word of `profiles.first_name` of the staff who own the client's projects (no emails, ids or last names), for the portal before the first update.
  - All four are security definer with an empty search path and fully qualified names; none can be called by anon. pgTAP 32 also lists every security-definer function a signed-in user can call (a tripwire: a new one must be added there on purpose).
  - The tables a client can read are still only `client_entitlements` (its own row).
- **Portal pages:** `/portal` and `/portal/market-report` read only through those functions and the client's own plan row (the Market Report, below, through its own functions). Staff "View as client" (`/client-access/[clientId]/preview`) uses the staff function and the same components, with no client session and no actions. `npm run qa:portal-scan` (local only) signs in as the demo client users and scans every portal page (HTML and RSC), every table, view and read function over the API, and guessed staff and other-client URLs for internal text, drafts, status words, other clients' names, unshortlisted partners and internal ids.
- **Built on the server, from an allow-list:** the browser sends only the form; the payload is rebuilt from live data on every preview and publish (`src/lib/client-updates/`). The loaders select named columns and copy only named fields, and the builders output a strict, versioned Zod schema (`payload-schema.ts`: every object strict, unknown keys refused before storing and again when rendering). The database backs this with `client_update_payload_ok()` (version, kind and top-level keys). Publish refuses unless the rebuilt update matches the previewed fingerprint, so nothing is published that wasn't previewed.
- **Never in a payload:** internal notes, assessment, next action, key notes, sources, key strength/weakness, assumptions, client decision, contact details of partners, internal ids, internal status words (Unfit, Do Not Contact, Withdrawn / No Response, Vetted, …), 3PL rate-card amounts (clients see only the percentage against today's rate card), and annual savings unless the expert ticks "include annual estimate". Partners are named only if shortlisted (enforced on the server); everyone else is a count, and ruled-out partners count as contacted only. Reasons and trade-offs are typed by the expert, never copied from internal fields. The contact line is the owner's first name (`profiles.first_name`) and an optional email typed on the form; account emails are never read.
- **Ranking gate:** only like-for-like quotes (agreed terms, forwarder still in the running, not expired on publish day) can be "best" or show a saving. Others are labelled. Minimum-data rules decide empty states in the builder, not only in the UI.
- **Integrity:** exactly one project per update; `client_id` is always the project's (trigger), `published_by` / `published_at` are the caller and now, published rows can't be edited or turned back into drafts, only admins delete a published update, at most one draft per project. A project's client can't be changed once an update has been published (`refuse_client_change_after_publish`), so the old client can't keep seeing a project that's no longer theirs. Writes need the project's owner or an admin (`can_write_client_update`). Only a write with no signed-in user (the local seed) may set past dates.
- **Tests:** `payload-allow-list.test.ts` builds payloads from full database rows with `INTERNAL-CANARY` in every internal field and checks the exact key paths (a new key fails until it's added on purpose), no canary, no status word, no unshortlisted name, no ids and no 3PL amounts; `project-panel.test.tsx` checks the rendered HTML the same way. pgTAP 31 covers the table rules.

### Client requests: what clients can write (Phase 3a)

Approvals, change requests and questions from client users, and Move's replies (`client_requests`). The first thing clients can write.

- **The table is staff-only** (standard restrictive policy; signed-in users get SELECT only, so staff read through RLS and clients get 0 rows; no INSERT, UPDATE or DELETE grant at all). pgTAP 28 and 34.
- **Clients write only through `submit_client_request(kind, engagement_key, update_key, message, wants_call)`** (security definer, `search_path=''`). It forces the client (`my_client_id()`), the author (`auth.uid()`), the time (`now()`) and the status (`sent`), builds the frozen decision copy itself (the update's headline and date, project kind and route, and the recommendation slice of its payload), and refuses with generic error codes:
  - `CQ403`: not a client, `must_change_password` set, or a project key that isn't one of the client's own (checked before anything else, so an outsider learns nothing);
  - `CQ409`: a decision on an update that isn't the project's latest published one, one without a recommendation, or a second decision on the same update (approving twice returns the first approval);
  - `CQ422`: an unknown kind or a bad length (question 1–1,000 characters, reason for changes 1–500, note up to 500);
  - `CQ429`: more than 10 requests per user per hour or 40 per client per day (under a per-client advisory lock).
- **Clients read through `my_client_requests()`**: opaque keys (request, project, update), kind, message, call flag, status, date, the sender's first name and whether it was the viewer, the approved recommendation's name, Move's reply with the replier's first name, and whether a reply was withdrawn. No ids, no staff ids, never a withdrawn reply's text. Coworkers at the same client see each other's requests (intended), with who sent each. Staff "View as client" uses `client_requests_for_client()` (the same rows, read-only, no buttons). Both wrap `client_requests_rows()`, which no signed-in user can call.
- **Immutable:** a trigger refuses any change to what the client sent (including the frozen copy). A reply is set once by `reply_to_client_request()` (project owner or admin); it can't be edited, only withdrawn by an admin with `withdraw_client_request_reply()`, which moves the text, its author and who withdrew it into the staff-only `reply_history` and sets the status back to `seen`. There is no delete. "Seen" is set by `mark_client_request_seen()` when the owner or an admin opens the request in the inbox (an explicit action; never a page render, a prefetch or View as client).
- **The portal functions** (`my_portal_updates()` and the staff twin) gained an opaque `update_key` (a hash of the client and the update id), added as the last column so the portal code deployed before it keeps working.
- **Scan:** `qa:portal-scan` fails if one client's request text or Move's reply to it appears for any other client, if a withdrawn reply's text (`WITHDRAWN-CANARY`) appears anywhere, or if the staff or write functions accept a client acting on another client's request or project.

### Introductions and Market Report interest (Phase 3b)

Two more kinds on the same staff-only `client_requests` table: a paid client asking Move to introduce it to a lettered partner of its Market Report, and a free client asking about the paid plan. The letter-to-forwarder mapping is the Market Report's secret (see below), so this is the first client write that touches it.

- **Writes only through functions** (security definer, `search_path=''`, explicit REVOKE from public and anon, on the pgTAP 32 tripwire). Both use the same shared checks as `submit_client_request()`: `client_request_caller()` (a client user with its own password chosen, else `CQ403`) and `client_requests_check_caps()` (10 per user per hour, 40 per client per day, counted across every kind, under the per-client lock). Neither is callable by signed-in users directly.
  - `submit_client_introduction(engagement_key, label, note, wants_call)`: the client must be on the paid plan, the key must be one of its own forwarder projects (`CQ403` otherwise, checked before anything else), and the letter must be a quoted or asked-to-quote anonymised row of that project's **latest** report: a letter only in an older report is `CQ409` (stale); a named, "Not taken forward" or unknown letter is `CQ422`. One open (not answered) request per letter per project, company-wide: asking again returns the open one. The database writes the client, author, time, status, the report id and a frozen copy of the row (letter, outcome, price, lead time, like-for-like), never a name.
  - `submit_market_report_interest(note, wants_call)`: not tied to a project; one per client ever (asking again returns it); refused (`CQ409`) on the paid plan.
- **Reads:** `my_client_requests()` (and the staff twin `client_requests_for_client()`) add `partner_label` as the last column: the bare letter. They return **no introduction rows at all while the client isn't on the paid plan**, so a free (or expired) client never receives a letter or a note that might mention one; the rows come back on upgrade. The forwarder's name is in no client function.
- **Staff:** the inbox resolves the letter through `market_report_partner_labels` (staff-only) and shows the name to staff only. A staff reply to an introduction is checked twice before the client can see it: the Server Action runs the "Move's take" guard (name words, HQ city, website and email domains, contact person) against the requested partner and every partner the latest report shows as a letter, with a staff-only error; and `reply_to_client_request()` refuses (`CQ423`) a reply containing the requested partner's full name, whatever the app does. Who may act (`can_act_on_client_request()`): the project's owner or an admin; for Market Report interest, an admin or the owner of any of that client's projects. Withdrawing a reply to an introduction is refused while a newer request for the same letter is open (it would reopen a second one).
- **Immutable:** the letter, the report id and the frozen copy can't change (trigger, table owner included).
- **Scan:** `qa:portal-scan` fails if a free client's HTML, RSC or any API answer contains a partner letter (`Partner D`), if any client receives the name of the forwarder behind any introduction request, or if `submit_client_introduction()` accepts another client's project (or the client's own on the free plan), or `submit_market_report_interest()` accepts a paid client.

### Market Report (paid plan, Phase 2c)

The Market Report shows a paid client every forwarder Move contacted for one forwarder project, with exact prices. It is the most sensitive thing a client sees (other companies' prices), so it has its own boundary.

- **Tables are staff-only:** `client_market_reports` (the payload, the expert's inputs, `published_by`, project ids) and `market_report_partner_labels` (which forwarder is "Partner E") keep the standard restrictive staff policy, so a client reading either directly gets 0 rows and can't write (pgTAP 28, 33). Reports can't be updated (no grant, and a trigger refuses it even for the owner); only admins delete one. Labels can't be updated or deleted by anyone signed in, and a trigger refuses any change except the foreign key nulling `forwarder_id` when a forwarder is deleted.
- **What clients can read:** `my_market_reports()`: the **latest** report of each of the caller's client's projects, only while `client_has_paid_tier(my_client_id())` is true (tier `market_report` and no end date or one in the future), with only `engagement_key` (the same opaque key as the project's updates), `published_at` and `payload`. Older reports never reach a client. Expiring the plan locks it at once; re-entitling unlocks it.
  - `market_reports_for_client(id)` (staff, "View as client") returns exactly what that client would get: nothing for a free or expired client. Both wrap `market_report_rows(id)`, which no signed-in user can call and which checks the plan itself.
  - `client_has_paid_tier(id)` answers non-staff only about their own client, so a client can't probe other clients' plans.
  - All are security definer, `search_path=''`, fully qualified names, revoked from public and anon; the three callable ones are on the pgTAP 32 tripwire. A forged `client_id` in `user_metadata` or the token gets nothing (pgTAP 33).
- **Free plan:** `/portal/market-report` reads only the plan row and renders a static locked page; no report function is called (`load-market-reports.test.ts`). A paid client asking for another client's project key gets a 404.
- **Anonymisation (built on the server, `build-market-report.ts`):** shortlisted forwarders (and the recommended one) are named. Every other forwarder is a letter and carries ONLY: the letter, the exact price, the lead-time range, a like-for-like flag, an outcome from a fixed list, a size band and a region from fixed lists, and the optional "Move's take". Unfit, Do Not Contact and Withdrawn / No Response all become "Not taken forward" with only the letter, outcome, size band and region (no price, lead time or take), and are counted as one number. Never: names, cities, websites, contacts, validity dates, incoterms beyond the flag, services, certifications, notes, statuses or ids. Strict schema (`market-report-schema.ts`), `market_report_payload_ok()` in the database, and `market-report-allow-list.test.ts`, which builds from full rows with a sentinel in every unused forwarder and quote column and checks the exact keys of each kind of row.
- **Letters:** handed out by `assign_partner_labels()` (the caller's rights, owner or admin, under an advisory lock) in the report's order, from D. A forwarder keeps its letter in every later report; letters are never reused (a deleted forwarder's stays reserved); a forwarder that joins the shortlist is named from then on. The preview computes the same letters, and Publish refuses if the letters it got differ from the preview.
- **"Move's take":** refused if it contains a word of any project forwarder's name (generic words like "Logistics" excepted), its HQ city as a phrase, its website or email domain, its contact person, or an internal status word (`market-report-guard.ts`), at preview and again at publish. The form says: "Write 'Move's take' as if the partner could read it. Don't mention anything that could identify them." Size and region are suggested from footprint and HQ, but only the fixed value is stored.
- **Scan:** `qa:portal-scan` checks, for every demo client user, that no anonymised partner's name, HQ (or city, unless it's on the client's own route), website or email domain or contact appears anywhere; that `REPORT-CANARY` (Ridgeway's report, free plan) and `OLD-REPORT-CANARY` (an older Brightline report) never appear; that free clients' HTML and RSC hold no report letters, prices or headings; and that the paid client really sees its report.
- **Accepted risk:** exact prices in a small market can hint at who quoted them (decided by Dani).

### Service-role exception: client users (`create-client-user.ts`)

- **Why:** creating an auth user (and setting its password or `app_metadata`) needs the Auth admin API, which only the service-role key can call. Logistics experts can create client users, so this is the first service-role path a non-admin can reach. It's built so it can't be turned into privilege escalation.
- **Where:** `src/lib/client-users/create-client-user.ts` only, called by the `/client-access` Server Actions after `requireStaff()`. It makes exactly three service-role calls, `auth.admin.createUser`, `auth.admin.getUserById` and `auth.admin.updateUserById`, and never touches data with the key.
- **Create** (`createClientUserAccount`, admins and experts): it checks the caller itself (staff); validates the client id, email and first name (Zod); reads the client **as the caller** (RLS); and for an expert requires a project they own for that client, in either module ("You can only add portal users for clients of projects you own"). It then **only creates**: an email that already exists is refused, never updated, so no existing account can be taken over or re-roled. The metadata is literal: `role: "client"`, `client_id`, `first_name`, `must_change_password: true`. Nothing from the input is spread into it, and `user_metadata` is never set. The database backs this up (the profiles foreign key and check).
- **Reset** (`resetClientUserPassword`, admins only): it re-reads the target's **stored** role and refuses anything but a client user with a client. It then sets only a new password and `must_change_password`; `app_metadata` keys merge, so the role and client are untouched.
- **One-time password:** 24 random URL-safe characters (`crypto.randomBytes`, 144 bits) plus a fixed tail, so letter, digit and symbol rules are always met. It's returned once in the action response and shown once (Copy, Done). It's never stored, logged or put in a URL; errors log only their code.
- **Tests:** `create-client-user.test.ts` checks the source. It pins the exact service-role calls, the two metadata literals, no spread and no `user_metadata`, the reset's role check before the update, and no password in any log line. It also checks behaviour: each caller type, expert ownership, tampered extra fields, an existing email, and that passwords never reach a log. `service-role-use.test.ts` lists the file; any other service-role use still fails there.
